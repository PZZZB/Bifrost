# 自动充值接入要求

状态：**服务端基础代码与离线验收已提供，尚未接入真实商户或开放自动充值**。现有主干新增订单、签名通知、主动查单和幂等入账；真实商户资格、密钥、正式交易及充值收银页面尚未完成。Mac 正在运行的服务没有启用收款。操作者不办理本人经营主体登记；无执照的个人接入按真实业务审核，不能把普通个人收款码当作自动支付接口。

渠道核对、完整费用和待发送的业务预审文本见 [个人线上收款渠道核对](payment-providers.md)。面包多 Pay 按用户要求保留作备选，尚未选定或支付新渠道开户费用。

## 已实现的服务端边界

- `src/payments/topups.mjs`：固定人民币商品、会话账号归属、客户端请求幂等、交易唯一性、先保存成功交易再写现有 `ClientBilling` 的入账任务；重启继续使用同一操作标识。金额是整数分，每分对应 10,000 微元，不保存另一份余额。
- `alipay.mjs`：官方 APIv2 的 RSA2 请求/通知与原始响应验签，扫码预下单、查单、关单；显式禁止 HTTP 重定向。原始签名 JSON 保留字节表示并拒绝重复外层字段。未把普通个人收款码变成接口。
- `wechat.mjs`：APIv3 Native，支持普通商户和服务商/子商户；应答和通知均验证固定可信公钥、时间戳与签名，通知通过 AES-256-GCM 解密。公钥轮换需由运营者可信更新私有配置；未知公钥不自动信任。
- `runtime.mjs`：主服务可选加载；不配置或禁用即关闭充值。每 15 秒启动一轮补偿，每轮最多 5 张未完成订单，禁止重叠轮询。保留平台中待确认的同一订单，不盲目重建支付订单。
- `http.mjs` / 网页接口：下单、本人订单查询走原 Cookie 会话与 CSRF；支付通知仅开放两个固定路径，验证支付签名，不接受浏览器“已支付”作为证据。现有公网转发仅向固定本机 43159 端口转发，不开放管理接口或任意目标。
- 已支付待入账或需人工处理的资金会暂停接收新充值；管理员现有账号快照增加支付状态计数。账号注销会阻止非零余额和未完成支付；已删除身份的后到付款保留原交易，进入处理状态，不充值给同邮箱新账号。

新增支付基础没有第三方运行时依赖，不涉及公司 Windows Desktop 网关、内部 CodeBuddy 凭据或模型请求转发逻辑。收银页尚未添加，用户正在调整的网页 UI 保持原样。当前两个 API 适配器也**不是** XorPay、YunGouOS 或面包多的接口适配器；选定并通过审核后再按该渠道实现收银和协议。

## 私有配置与接口

仅服务端读取 `BRIDGE_PAYMENTS_CONFIG` 指向的绝对路径；参考 [禁用配置示例](../examples/payments/config.example.json)。配置文件及密钥要求本人所有、文件 0600、私有目录 0700。示例默认禁用、没有商品，不含凭据。主服务复用 Mac 账号网页的 HTTPS 主域名。

获批后的运营者需要配置真实商户、已批准的支付产品、私钥/支付平台公钥及需要销售的固定商品。商品格式为 `{ "id": "cny-10", "title": "实际商品名", "amountFen": 1000 }`，这只是格式示例，尚未确定正式售价。微信服务商模式中 `mchId`、`appId` 是签名服务商的信息，`subMchId` 为实际收款商户。需先开启该 Bifrost 账号的余额计费，再允许下单；充值不替代模型定价设置。

| 接口 | 方法 / 权限 |
| --- | --- |
| `/account/web/v1/topups` | GET：已登录用户的商品、渠道与最近本人订单；POST：会话 + Origin + CSRF，仅接受 `channel`、`product`、UUID `requestId` |
| `/account/web/v1/topups/<32位订单号>` | GET：本人订单；不能跨账号查询，不返回支付密钥、入账操作 ID 或付款人资料 |
| `/account/web/v1/payments/notify/alipay` | POST：支付宝 form 通知 + RSA2 验签 |
| `/account/web/v1/payments/notify/wechat` | POST：微信原始 JSON、签名请求头与加密交易校验 |

通知和主动查单必须走同一笔订单和同一入账幂等标识。有效期到后隐藏付款指引，由渠道确认关单；不把超时当作未扣款。若渠道确认此前未创建订单且已关单，清理该待处理状态；真正的迟到成功通知仍保留并处理。

`payment-orders.json`、真实支付配置、引用的全部密钥/证书需要加入现有加密备份清单并演练恢复。没有批准商户时不创建或部署真实支付配置。订单与 `ClientBilling` 必须由同一主进程独占维护；不支持多个独立进程共用这些文件，也不应单独运行第二个回调进程写余额。

退款、投诉、被删除账号的后到款及资金争议仍需补齐运营处理流程；当前不会自动退款或擅自扣减已使用余额。正式上线还须完成真实商户沙箱、小额正式支付、退款、通知可达性、域名权限、财务记录保留/隐私说明和备份验收，不能把离线测试当作已完成这些项目。

## 已确定的产品要求

用户在网页付款成功后自动增加本人账户余额，不经过人工审核。服务器收到可验证的成功交易结果后立即入账，页面自动刷新；平台通知延迟或短暂网络故障时，通过签名查单补偿。浏览器“已支付”、支付成功跳转、截图或单纯收款提示不构成入账依据。

支付订单绑定创建它的已登录 Bifrost 账号，和付款人的微信昵称、支付宝昵称不是同一身份。别人替用户支付这张订单，仍充值到订单绑定的账号。账号 ID 由服务端会话确定，不能由前端传入任意目标。

```text
已登录账号 → 创建充值订单 → 支付机构收银台
                     ↓                ↓
              订单绑定 accountId ← 可验证的成功通知 / 官方查单
                     ↓
          幂等入账到现有 ClientBilling → 页面显示新余额
```

## 商户与支付场景

面向微信内打开的网页，常规直连使用 JSAPI 支付；需要商户号、对应支付产品权限、已认证并与商户绑定的公众号 AppID，以及支付授权目录等配置。它不是重新注册小程序。申请主体、真实业务类目及所需资质由支付平台审核。

用户已明确不办理本人经营主体。若考虑服务商的小微或平台个人入驻，必须另行确认线上支付、业务类别和回调权限；微信普通小微通道的线上虚拟行业限制也必须核实，不能因能展示收款码或基础权限支持 JSAPI 就认定 API 额度充值可受理。支付宝需要另核实适用的线上支付产品及签约权限，不套用微信的审核结论。

技术参数和密钥在正式商户开通后保存到私有配置，不写聊天、网页源码或 Git。尚未配置有效商户时，真实充值入口保持关闭。

## 订单、金额与账本

- 服务端生成唯一订单号，固定保存账号 ID、商户与渠道、人民币金额（整数分）、入账微元、商品/费率版本及有效期。
- 当前余额以人民币微元记账：`1 元 = 1,000,000 微元`。充值金额、到账余额及任何优惠必须在下单时明确并冻结，不能在回调中使用前端给出的金额。
- 验证通知签名、必要的报文解密、商户/AppID、订单号、交易状态、币种及金额。交易号按渠道和商户唯一，不能用于多张订单或多个账号。
- 使用现有 `ClientBilling.adjustBalance`，固定 UUID `operationId`、账号和金额；同一操作重试不会重复入账，冲突则拒绝。
- 先持久化验证后的交易和固定入账操作，再提交既有账本，最后标记订单已入账。服务重启后重试同一操作标识，不建立第二套可独立修改的余额库。
- 充值不自动提高上游官方额度，也不绕过账号停用、模型权限、Token 限额或价格规则。正式收费前需要配置真实销售商品、费率和余额限制。

## 接口及故障边界

下单、订单查询和余额读取使用当前用户会话、CSRF 与账号归属检查。回调单独发布固定 HTTPS 路径，只接受对应支付机构的验证协议；不发布管理员记账接口，不以用户 API Key 替代支付签名。

通知先返回成功必须以交易及入账任务已经持久化为前提。重复、乱序、伪造通知以及回调失败后的主动查单均走同一幂等处理。支付平台通知不可达时不会把未知状态当作已付款；恢复后自动查单。订单过期、退款、账号删除及支付后失败需要明确状态和资金处理，不静默丢弃已收到的款项。

应验收：伪造签名 / 错误金额不入账、真实成功立即增加正确账号余额、重复通知只入一次、跨账号不能查单、重启中断不重复入账、通知丢失能够补单，以及实际商户沙箱和小额正式交易。上线前还需验证当前公网入口的回调可达性和支付授权域名要求。

官方参考：[微信 JSAPI 权限申请](https://pay.wechatpay.cn/doc/v3/merchant/4012791854)、[微信商户入驻材料](https://pay.wechatpay.cn/static/applyment_guide/applyment_detail_public.shtml)、[商户下单与结果通知参数](https://pay.wechatpay.cn/doc/v3/merchant/4012525171)。这些材料说明支付接入要求，不代表本项目的经营范围或商户资质已经通过审核。

对外收费的模型来源授权需另行确认。Claude 个人订阅条款限制将账号提供他人及转售服务；办理营业执照不会自动获得此类上游授权，应使用明确允许相应用途的商业/API服务安排。参见 [Anthropic 个人服务条款](https://www.anthropic.com/legal/consumer-terms)。
