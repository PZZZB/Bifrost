# WorkBuddy 客户端

2026-11-01，使用官方签名的 Apple 芯片版 WorkBuddy 5.9.3，在实际桌面客户端中通过公网 Bifrost 用户 API 完成 Claude Sonnet 聊天和 Claude Opus 文件工具回合。使用独立注册用户的普通 Key；客户端不持有 VM 私有网关凭据。工具在 WorkBuddy 所在电脑执行，Claude 继续在隔离虚拟机内通过既定 VPS 出口运行。

## 配置

1. WorkBuddy 登录后打开“设置 → 模型 → 添加模型”，供应商选“自定义”。
2. 接口地址填写用户中心显示的完整 HTTPS Chat 地址，以 `/v1/chat/completions` 结尾；API Key 填本人的 Bifrost 用户 Key。
3. 模型名填写精确路由 ID，例如 `Claude-sonnet` 或 `Claude-opus`。每个模型分别添加；模型与能力以管理员授权和服务端实际目录为准。
4. 标准地址保持“自定义协议”关闭。工具、图片和上下文预算按所选来源已确认的能力配置。
5. 回到新任务，在模型列表底部的“自定义模型”分组选择对应模型。

当前版本的模型文件为 `~/.workbuddy/models.json`，与 CodeBuddy 的 `~/.codebuddy/models.json` 分开。文件包含调用 Key，不能放进项目仓库或发送给别人。

官方依据：[模型配置](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Model)、[版本下载](https://www.codebuddy.cn/docs/workbuddy/Download-History)。Windows 客户端尚未现场验收；不能用本机 macOS 结果代替。

## 已修复的兼容问题

- WorkBuddy 的 SDK 与链路追踪头超过原入口 40 项限制，会触发 HTTP 431。公网入口现允许最多 128 项，仍保留原 16 KiB 总字节限制。无效 Key、重复认证头和超大请求头仍被拒绝；无关客户端头不会传给模型来源。
- WorkBuddy 会同时发起主对话和辅助请求。本机每用户并发从 1 调整为 2，网关总并发仍为 4。其他部署应结合自身资源配置，不能按客户端名称跳过限流。
- 上游会话冲突保留 HTTP 409。没有模型输出或实际用量的明确冲突释放预留；带真实用量的错误仍按用量结算。网络中断和未知错误继续保留待核对状态，不伪造 Token。

## 验收范围

实际客户端选择了 `Claude-sonnet` 并收到指定测试文本。Opus 使用专门测试工作空间，读取由验收脚本创建、未写入提示的随机标记文件，返回正确标记；没有让它读取用户项目或其他文件。

随后更新同一测试文件的随机标记，在同一 WorkBuddy 会话再次读取并返回新值，验证工具继续对话。最后一轮共 3 次实际请求，均完成用量结算；没有新增待核对请求，账号预留为 0。客户端的辅助调用同样作为独立请求计费，不按一次界面操作合并为一笔。

“测试连接”按钮收到首个有效 SSE 片段就会取消读取，不能据此证明完整推理、工具接续或用量结算。此次以真实任务及服务端账本为验收依据；测试中的人工预留处理另保存在本机私有审计记录，不能当作自动计费验证结果。

## 模型列表边界

Bifrost 的 `/v1/models` 始终按当前用户权限返回模型，新增或停用立即影响服务端授权。WorkBuddy 5.9.3 的原生自定义入口要求具体模型 ID；未验证“只填 URL＋Key 自动增删整个列表”。该能力需要客户端自身读取并刷新目录。

先前在远端用户电脑运行的模型文件同步器已撤销。普通公网接入仍只保存一次客户端配置；运行 Bifröst 的本机另提供[统一客户端管理](local-client-controls.md)，网关模式可自动或手动维护 WorkBuddy 模型文件，不能据此宣称公网客户端会自动发现目录。WorkBuddy 作为调用客户端的支持，不等于把 WorkBuddy 的厂商账号当作上游额度来源，也不代表图中所有其他供应方都完成了产品验收。
